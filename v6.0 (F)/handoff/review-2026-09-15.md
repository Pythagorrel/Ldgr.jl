## Context

ldgr is the clinic's daily cash-entry tool (Julia server + plain HTML/JS form, `E:\Ldgr\v4.0`). Since 2026-09-15 the Review and Saved screens are gone: **Save & next day** writes each day straight to the books through `POST /api/save`, and every save already carries the date and a typed reason for each difference (`reason` for a day that doesn't balance, `openingReason` for an opening that doesn't match the last close). The owner asked for five things:

1. An architecture for **emailing the client when a saved day has a difference**, giving the day and the reason.
2. A **codebase review plan** that identifies bugs (functional or visual; backend, front end or end-user) that stop the program doing its job.
3. **Improvements to the diagnostic tips** (Level 4 hints such as "the difference matches one of your figures").
4. **End-user scenarios** that show every error catch and the ordinary, calm path.
5. The **lag on Save & next day** since the Review screen went: cause and best fix.

Everything below is analysis and design. Nothing in the repo has been changed. The work was done by one main session plus three Opus review passes (backend, front end, scenarios and hints), with timing probes run in-process against a scratch `LEDGER_ROOT` (nothing was written under `v4.0/Records`). Items marked **[owner decision]** need the owner's word before implementation.

Constraints that shaped every recommendation (CLAUDE.md, README rules, saved owner preferences): never compute, re-derive or pre-fill a closing or opening balance; each Level 2 difference keeps its own reason box beside its figure; no warning codes on screen; plain words ("Work day"/"Off day", "Start of day"/"End of day"); one primary action; nothing floats; no new colours; no extra features without asking; no message that repeats a prompt already on screen; don't warn about a box before it has been left or Save pressed; never build a path outside `Layout.jl`; the server binds 127.0.0.1 only; keep the REPL start path and the chromeless window launcher.

## 1. The Save & next day lag — measured cause and fix

### Measurements (Julia 1.9.2, this machine, endpoints called in-process through `router(HTTP.Request(...))`, no port bound)

| Call | As the code is today | After the fix below (measured) |
|---|---|---|
| `include("server.jl")` (package load at server start) | 7.4 s | 7.4 s (only a sysimage removes this) |
| `POST /api/check`, first call | 2.5 s | 10 ms |
| `POST /api/save`, first call | **5.2 s** | **285 ms** |
| `POST /api/check`, first call on a day with a difference | 1.5 s | 119 ms |
| `POST /api/save`, first save of a day with a difference | 824 ms | 753 ms (residual, see option B) |
| `POST /api/save`, first Off day | 457 ms | 185 ms |
| `POST /api/save`, first edit of a saved day | 760 ms | 24 ms |
| `POST /api/save`, first refusal (no reason / Must-fix) | 183–392 ms | 4 ms |
| `POST /api/save`, warm, any kind (30-row journal, cross-month too) | 40–67 ms | same |
| `POST /api/check`, warm | 2–8 ms | same |

Warm-save breakdown: `day_findings` 4 ms, `process_day` 26 ms, `Report.write_report` 31 ms; one journal parse ≈ 2 ms; a save parses the month's journal 13–19 times and a check 4 times (wasteful, but ~30 ms in total).

### Diagnosis (two causes, both compile-time, neither the bookkeeping)
1. **Julia compiles each save path the first time it runs after the server starts.** The Review screen used to pay this once per batch on "Save to the books"; now it lands on the first **Save & next day**, plus the daily report is written on every save. During development the server is restarted after every Julia edit, so the owner meets the cold path constantly.
2. **The JSON responses change *type* with the data, and JSON3 compiles a new writer for every new shape.** Verified: writing a findings list whose `field` values are all strings costs 606 ms the first time, a list with a `null` field another 545 ms, and a check response with `predicted: null` versus `predicted: 1234.5` are two more separate compiles (72 ms and 195 ms). `findings_json` in `server.jl` builds the list by comprehension, so its element type depends on which warnings fired; `handle_check`'s response is a NamedTuple whose field types depend on whether the balances are blank. That is why the first save of *each kind* (balanced, with a difference, Off day, edit, refusal) each paid its own 0.4–2.5 s in the first probe even after the pipeline had run once.
3. The form gives no sign that anything is happening: `saveDay` sets a `saving` flag, but `updateButtons()` never reads it, so the button keeps its label and green fill and a second click is swallowed silently (`app.js:329-331`, `979-983`). A 5 s wait reads as a hang.

### Fix (recommended, in this order)
1. **One JSON shape per endpoint** (`server.jl`, ~20 lines). `findings_json` returns a vector with a declared element type (`NamedTuple{(:code,:level,:levelName,:title,:field,:message), Tuple{String,Int,String,String,Union{Nothing,String},String}}`), and `handle_check` builds its response as `Dict{String,Any}` (or a fixed-type struct) so `predicted`/`available`/`paidOut` being `nothing` or a number no longer changes the type. Same for the 400 bodies that carry `findings`. The browser sees identical JSON.
2. **Warm up at server start** (`server.jl`, new `warmup()` called from `start()` before `HTTP.serve`; `LDGR_NO_WARMUP=1` skips it for quick dev restarts). It writes nothing to the books: it calls the real read-only endpoints through `router` (`/index.html`, `/api/config`, `/api/prior`, `/api/day`, and `/api/check` for a balanced day, a day with a difference, a blank closing, a Must-fix, an Off day and two bad bodies), runs `check_day` on synthetic records with synthetic priors (first day, day with a prior close, ledger exists), does `upsert_day!` on `empty_journal()`, round-trips a journal frame and two ledger frames through `CSV.write`/`read_journal` on a `mktemp()` file (the same methods the real files use), builds a report with `Report.build_report`, serialises the save-shaped responses, runs one `@warn` through `CollectLogger`, and `precompile`s `process_day`, `_write_daily_ledger!`, `_retry_pending!`, `handle_save`, `write_report`, `write_ledger_csv` and `write_journal` (all eight returned `true` in the probe). Cost: 8–10 s once at startup, printed as one line ("Warming up the checks and the books… done"). Run it synchronously: Julia is single-threaded here and compilation does not yield, so a background warm-up would stall the page's own first requests. `mktemp()` is Base, not a Records path, but to honour rule 2 give it a name in `Layout.jl` (`warmup_file()`).
3. **Show the save happening** (`app.js`): while `saving` is true, disable `#btn-next`, set its text to "Saving…" and `aria-busy="true"`; make `updateButtons()` compute `disabled = saving || !formValid()` so a keystroke cannot re-enable it mid-save; restore the label in `finally`. Also move the Off-day `confirm()` before the pre-save check (a closed day cannot raise a Level 1 or 2 finding, so the check buys nothing there and the question feels instant).
4. **Option B, only if the ~0.3–0.75 s residual on the first save of each kind still bothers the owner:** make the Records root switchable (`Layout.root()` reading a `Ref`, all `Layout.ROOT` uses updated) so `warmup()` can rehearse four real saves against a temporary Records folder and then switch back and delete it. That compiles everything and the first real save is ~50 ms. More invasive, so second choice.
5. **Go-live step: a PackageCompiler sysimage** built with `warmup()` as the precompile-execution file. It removes the 7.4 s load and every residual compile. `server.jl` already anticipates this (`browser_candidates` comment). Keep `include("server.jl"); start()` working.
6. Not the cause, but worth doing together with the journal fixes in §3: one `prior_record` lookup per request instead of five to seven (`Chain.prior_day` and `Chain.is_genesis_date` each re-parse the journal; `handle_check` calls `is_genesis_date` twice and `in_books` once more), a `(path, mtime, size)` memo in `read_journal`, a process-wide lock around journal read-modify-write, and write-temp-then-rename in `write_journal`. Optional and not recommended now: skipping the pre-save `/api/check` in `saveDay` when the on-screen findings already match the figures **and** the date (today `state.checkedFor` records the amounts but not the date, see §3.2).

### Verification
Re-run the in-process timing probe (scratchpad `probe3.jl`, run with `LEDGER_ROOT` set to a scratch folder) after steps 1–2: first `/api/save` of each kind should be under ~300 ms (under ~800 ms for the first day with a difference). Then start the server normally with a scratch `LEDGER_ROOT` and `LDGR_NO_BROWSER=1`, and time the first Save & next day in Chrome DevTools for a balanced day, a day with a difference, an Off day and an edit; confirm the button reads "Saving…" during the wait and that a double-click does nothing.

## 2. Email when a saved day has a difference — architecture

### Where the facts already exist
`process_day` (`main.jl:217-231`) returns, per saved day: `date`, `closed`, `journal` (`"added"`/`"replaced"`), `daily_ledger`, `day_variance`, `overnight_variance`, `reason`, `opening_reason`, `released` (held days whose ledgers this save produced), `findings`. `handle_save` (`server.jl:456-481`) receives that outcome after the day is in the books and after `Report.write_report`; `main()` (`main.jl:372-378`) gets the same outcome on the command line. "This day is not balanced" is exactly the condition `main.jl:164` and `Report.jl:91` already use (`abs(v) >= 0.005`; use `!Checks.is_zero_money`). Both reasons are guaranteed non-blank for their difference because `Checks.unexplained` refuses the save otherwise, so "unexplained difference" in the feature means *a difference that was posted to Cash Over/Short together with the typed reason* (a reason-less difference cannot be saved at all) **[confirm with owner]**. `Report.jl:82-100` already renders each difference with its own reason ("SHORTAGE of $1,900.00 during trading / reason: Could not locate"), and its header says: "When email is added it should send THIS text and not assemble its own."

### Design
New module `v4.0/Notify.jl` (included from `main.jl` after `Report.jl`), one entry point called by both front doors right after the report is written, wrapped exactly like the report call so a failure can never fail a save:

- `Notify.after_save(outcome; previous=nothing)` → does nothing for an Off day or a day without a difference; otherwise builds one message and queues it. `previous` is the day's earlier journal row (read in `handle_save` with `saved_record(d)` before `process_day`) so a re-save whose variances did not move sends nothing, and an edit that turns an unbalanced day into a balanced one can send a short "now balances" notice.
- **Message** (plain text): subject `ldgr: 3 September 2026 did not balance (shortage $1,900.00)`, with `(updated)` when `journal == "replaced"`. Body: the day; each difference on its own line from a new `Report.difference_lines(outcome)` factored out of `build_report` (so file and inbox never drift); who entered it (`USERNAME`) and when, stated as clinic local time; the day's figures and the predicted closing (via `Checks.money`, `Checks.predicted_closing`) so the owner can judge without opening the books; then the full daily report text under a rule. Money through `Checks.money` everywhere (fix `Report._money`, which prints `$1270.0` and `$1.0e6`; see §3.1 #9).
- **Queue, then send, never block.** `Notify.enqueue(msg)` writes the message to `Layout.outbox_dir()` (`<ROOT>/Notifications/outbox/<yyyy-mm-dd HHMMSS> <day>.txt`, a small header block with to/subject/attempts, then the body). Cheap, local, synchronous. `Notify.flush!()` sends every outbox file through the transport, moves sent ones to `<ROOT>/Notifications/sent/`, leaves failures for retry, logs to the audit log and console, and raises one `@warn` in plain words ("The owner could not be emailed just now. It will be sent on the next save.") which `CollectLogger` already carries to the save banner. `flush!` runs `@async` after `handle_save` has composed its response, at server start, and after every later save, so an internet outage delays a notice rather than losing it. Paths come from `Layout.jl` (`notify_config_path`, `outbox_dir`, `sent_dir`).
- **Settings**: `v4.0/notify.toml` (stdlib `TOML`, no new dependency), git-ignored, with `notify.example.toml` committed: `to`, `from`, `smtp` (e.g. `smtps://smtp.gmail.com:465`), `user`, `password` (an app password), `subject_prefix`. No file → notifications off; `start()` prints `Email notifications: off (no notify.toml)` or `on → owner@…`. The password is never logged.
- **Transport** behind `Notify.TRANSPORT[]::Ref{Function}` so tests inject a capture function. **[owner decision — transport]**
  - *Recommended:* **SMTPClient.jl** (libcurl; one `Pkg.add`) with the clinic's own mailbox and an app password. No third-party account. Caveat: libcurl's send does not yield to Julia's scheduler, so the 1–3 s send briefly holds the server; because it runs after the save has been answered, the only visible effect is that the next day's prior-day hint can appear a couple of seconds late, and only on days with a difference.
  - *Alternative:* an email API over HTTP.jl (already a dependency; Brevo/Resend/Postmark), which yields properly and needs no new package, but needs a third-party account and API key.
  - *Not recommended:* PowerShell `Send-MailMessage` (obsolete cmdlet, credentials on a command line).
- **When to send** **[owner decision — policy]**: always on a save with a difference (the ask); again on an edit whose figures or reasons changed, marked "(updated)"; *recommended:* once more when an edit makes a previously unbalanced day balance. Never for Off days, never for refused saves (nothing was written).
- **Released held days.** When a missing day is entered, `_retry_pending!` (`main.jl:292-360`) re-derives the *next* day's overnight variance against the now-known prior; that is a newly discovered difference on a different date and today it is only a log string, and a held-for-a-reason day (`main.jl:330-334`) is logged only. Before wiring email: widen `released` to carry `(date, day_variance, overnight_variance, reason, opening_reason)` and return the held-for-reason days as a `held` field, so `after_save` can notify about those too and the report can list them. (This also feeds the front-end message in §3.4 #7.)
- **The CLI front door** cannot reach this feature until §3.1 #17 is fixed: the CSV and interactive paths never read or ask for a reason, so any day with a difference errors out before `process_day` returns.
- **The form**: nothing changes by default. The save response can carry `notified: "queued" | "off"`. Whether the banner should add "The owner has been told." is **[owner decision — form]**.
- **Tests**: `tests/test_notify.jl` with the capture transport: balanced day → nothing; day difference → one message with the date and the reason; both differences → both lines; Off day → nothing; re-save with unchanged variances → nothing; edit to balanced → "now balances"; transport failure → file stays in the outbox and the next `flush!` sends it; missing `notify.toml` → off and the save still succeeds; `Report.difference_lines` identical to the report file.
- **Docs**: README "Requirements" (SMTPClient) and a "Notifications" section; `.gitignore` entry for `v4.0/notify.toml`; CLAUDE.md note.

Files touched: new `Notify.jl`, `notify.example.toml`, `tests/test_notify.jl`; edits to `Layout.jl` (three paths), `Report.jl` (factor `difference_lines`, use `Checks.money`), `main.jl` (include; widen `released`; call in `main()`), `server.jl` (previous row + call in `handle_save`; drain at `start()`; startup line), README, `.gitignore`.

## 4. Diagnostic tips (Level 4) — what is wrong and what to do

Findings (probed): the divisible-by-9 tip fires for about **11 %** of arbitrary differences (one genuine clinic difference in nine is told "digits may be swapped"), has no size floor ($0.09, $9, $18 all fire) and never names a box. The "matches one of your figures" tip is blind to sign and to which side of the identity the figure is on, includes the counted balances and variances in `typed` (nonsense like "Opening Balance … entered twice"), duplicates the card tip whenever one POS box is filled, and misses cash sales genuinely entered twice (the difference is half the figure). The "nine times" tip catches only ÷10 slips, not ×10, and misfires on small boxes ($450 short with a $50 taxi fare → two wrong tips). Hints run on the overnight difference against *today's* figures, which cannot explain it. Any Must-fix suppresses every hint, so the day that most needs help gets none. There is no cap. All proposals stay Level 4, never block, plain words, no codes on screen.

# ldgr — project notes for Claude

ldgr is a small Julia bookkeeping tool for an urgent care clinic. Staff type each day's cash figures into a local web form. The program checks the day, then writes a Daily Journal and ledgers that can be imported into QuickBooks.

This folder is a sparse checkout of `github.com/Pythagorrel/Ldgr.jl` (branch `main`) with only `v4.0/` checked out.

**The program folder is now `v5.0/`** (renamed from `v4.0/` in early October 2026, and not yet tracked by git). Every `v4.0/` path below means `v5.0/`.

- **Send time 17:30** (`Notify.DEFAULT_SEND_AT = Time(17, 30)`), the developer's choice on 2026-09-28; `send_at` in `notify.toml` overrides it. The times the report prints ("5:30 pm") come from the configured time, never a literal. The healthchecks.io schedule must match: `30 17 * * 1-6`, America/Guyana.
- **How it is sent:** while the server runs, the coming report is handed to Resend with `scheduled_at` set to the next send time, and Resend sends it then even if ldgr has been closed. Each save hands over a fresh version and cancels the old one. A report is handed over on every day ldgr is opened, even with no saves, so a quiet day still sends; if ldgr is not opened at all between one send time and the next, nothing goes out and the watchdog alerts.
- **`Resend.jl`** (new, `module Resend`) is an HTTP client for two calls: `send(key, email; idempotency_key) -> id` (`POST /emails`) and `cancel(key, id)` (`POST /emails/{id}/cancel`). `cancel` returns normally only for a 2xx, or a 4xx other than 401/403/408/429 (nothing is left to cancel); a 3xx, those four and a 5xx throw, so an earlier version is never recorded as cancelled unless Resend said so. `API_BASE` and `TIMEOUTS` are Refs so tests can point it at a stub. Every failure is a `Failure(kind, words)`, `kind` `:settings` or `:temporary`, with one plain sentence that never contains the key: Resend's own message is scrubbed before it is shortened, and anything shaped like a key (`\bre_[A-Za-z0-9_]{8,}`) is masked, here and in `Notify._scrub`. A certificate that could not be checked (`OpenSSLError`/`MbedException`, unwrapped through `RequestError`, `CapturedException`, `CompositeException` and `TaskFailedException`) gets its own sentence pointing at the computer's date and time and at antivirus software that inspects HTTPS, not "the internet could not be reached"; a ConcurrentUtilities `TimeoutException` counts as a timeout. `server.jl` includes it right after `main.jl` and fills `Notify.MAILER[]`; `main.jl` never loads it, so the CLI never sends.
- **`notify.toml`:** `to`, `api_key` (a Resend **Full access** key; a sending-only key almost certainly cannot cancel; the first live run confirmed that a Full access key can), `from` (required since 2026-09-29, with no fallback; the developer's is `LDGR Daily Report <reports@…>` on a verified domain), `subject_prefix`, `send_at` (`"HH:MM"`; an unquoted TOML time is cut to whole minutes, or it would never match the state file and every tick would hand over a new version). Email needs `to`, `api_key` and `from`. **`from` must be an address on a domain verified in Resend,** and a file without one is off ("notify.toml has no from address"): `Notify.DEFAULT_FROM` is gone, because the shared testing sender it named, `onboarding@resend.dev`, sends only to the account's own address, and on the first live run (2026-09-29) a scheduled report from it was accepted and then failed at its send time with "Domain is not verified", which ldgr cannot see (only the watchdog can). An old SMTP-style file counts as off. `Notify.banner()` is the start-up line: `on -> <to>  (daily report at 17:30, sent by Resend; last complete report: …)`, or `off (<why>)` (`no notify.toml`, `notify.toml has no Resend api_key`, `… has no to address`, `… has no from address`, `… could not be read`), with `[not scheduled: LDGR_NO_DIGEST=1]` appended when that is set. `notify.example.toml` holds the setup checklist.
- **State that survives restarts,** under `<ROOT>/Notifications/` (paths in `Layout.jl`; the outbox/sent paths were deleted and `scheduled_state_path`, `temp_path` added), each written to a temp file and put in place with `Base.Filesystem.rename`, not `mv(...; force = true)`, which on Julia 1.9 deletes the old file before renaming, so a crash or a virus scanner holding the new file could leave neither:
  - `last report.txt`, the marker: how far reports are known to be complete, meaning handed over **and** past their send time. A marker more than 5 minutes in the future is ignored, with a note in the report.
  - `scheduled report.toml`: the waiting version's `id`, `cutoff`, `from`, `rows` (change-log rows in its window when built), `problem` (what `rows_checked` could not read when it was built, `""` when nothing), `generation`, a `settings` fingerprint of `to`/`from`/`subject_prefix` (a change replaces the waiting version), `[[cancel]]` tables (id and cutoff) of earlier versions still to cancel, `unsure` (only while set; see step 0), and, while a hand-over is unconfirmed, a `[pending]` table: `kind` (`scheduled`/`late`/`fix`/`now`), `key`, the exact email fields, `from`, `cutoff`, `rows`, `problem`, `generation`, `settings`, `written`. `[pending]` is written before every send and cleared in the write that records the answer, or at once when nothing can have been made: a `:settings` refusal, or a request that never left the PC (`Resend.Failure`'s third field `reached` is false for a `ConnectError`: no DNS, refused, connect timeout, TLS handshake). It exists because an answer lost to a dropped connection would otherwise let the next rebuild, with different content and key, become a second email. A missing or unreadable file is replaced at once, with the generation seeded from the clock, so a lost file can never rebuild an idempotency key that Resend would answer with an already-cancelled email.
- **`Notify.tick(; at = nothing, force, poked)`** takes the `BUSY` lock and only then reads the clock (`at = nothing` means now), because a poke can wait behind a tick stuck on the network. Re-deriving everything each time, it runs step 0, then four steps:
  0. **Replay an unconfirmed hand-over.** A `[pending]` one is sent again with the same key and a byte-identical email (`Notify._email_dict` builds the Dict in one fixed key order). On success it does what the first success would have done: a scheduled one becomes the waiting version (`_adopt!`; the previous one goes to cancel, and step 1 then cancels at once, ignoring the cancel pause); late/fix/now move the marker, and a fix also clears the waiting state. A `:settings` refusal drops it, with an audit line and no global pause; a `:temporary` failure keeps it, starts the 5-minute pause and stops the tick; one older than 23 h (Resend forgets a key after a day) is dropped with an audit line. **A scheduled one whose send time has come (under a minute away) is never replayed** — it would carry a `scheduled_at` in the past, which Resend might send unlabelled, hold or refuse. It is dropped with an audit line, and steps 2/3 send what it held as a labelled corrected or late report. Its send time is kept in `Scheduled.unsure` (as is a scheduled one's dropped for being older than 23 h), because Resend may still send it; `unsure` is cleared once the marker reaches it. Every report ldgr builds whose window `(from, cutoff]` contains `unsure` carries one sentence about the possible repeat (`_repeat_note`, joined to other notes by `_notes`): a late report says "This report may repeat one sent at 5:30 pm: ldgr could not confirm that Resend had received it …" in place of "This report is late …"; corrected, follow-up, forced and first-ever reports add it to their own note; a scheduled version for that same send time says "Two reports may arrive at 5:30 pm: …". Two cases carry none: a version step 2 settles without sending anything, and a version already waiting when `unsure` is set (step 4 does not rebuild just to add the note).
  1. Cancel leftovers, dropping any whose send time has passed.
  2. Settle a version whose send time has passed. More rows in its window now → a **corrected** report at once (subject "corrected report for", note "This replaces the report sent at 5:30 pm, …"). Otherwise, a **fresh** problem (non-empty and not the version's own `problem`) → a **follow-up** at once, not marked corrected ("This follows the report sent at 5:30 pm. When ldgr checked it afterwards, part of the change log for that stretch could not be read, …"). Otherwise the marker moves.
  3. A closed stretch nothing covered goes at once as one **late** report (the very first report is "the first report since email was set up"), or **folds** into the coming report if nothing was saved in it and the log was readable.
  4. Hand the coming report over when its window, row count, `problem` or settings changed (new version first, then cancel the old). `next = next_cutoff(marker === nothing ? ripe : max(ripe, marker), send_at)`, so a clock stepped backwards never schedules a send time the marker has passed. Nothing is handed over when `next - (at + (now() - started)) < 1 minute`, judged against the time now because steps 0–3 may have waited on the network; step 2 takes over.

  **A send time counts as passed only once its whole second is over:** `ripe = floor(at, Second) - Second(1)`, step 2 settles only when `cutoff <= ripe`, and step 3's `due = latest_cutoff(ripe, send_at)`, because the log stamps rows to the second and a save at 5:30:00.6 belongs to the 5:30 report. `force` reports up to `floor(at, Second)` and marks that. `tick` returns symbols from `:off :no_mailer :waiting :cancelled :settled :sent :late :scheduled :failed :idle`.
- **Idempotency keys are deterministic** (`ldgr-<yyyymmddHHMM>-g<generation>-<16 hex of sha256(from|to|subject|text|scheduled_at)>`, and `ldgr-late-…`, `ldgr-fix-…`, `ldgr-now-…`), so the body holds no "prepared at"; it says "Includes everything saved up to 5:42 pm on 28 September" from the last row in the window instead. `scheduled_at` is the send time in UTC, using the machine's offset at call time.
- **Failures:** a `:temporary` one pauses hand-overs 5 minutes (a save's poke skips that pause); a `:settings` one pauses 60 minutes or until `notify.toml`'s modified time changes (a poke does not skip it). Cancels have their own pause and their own audit throttle (`CANCEL_BACKOFF`, `LAST_CANCEL_TROUBLE`), so a hand-over that works does not make the same cancel failure news again; both are cleared when a cancel is tried and works, and step 4 always tries cancels at once. The audit log (header "email") and the terminal get a failure's sentence only when it changes or an hour has passed. An error nobody planned for (not a `Resend.Failure`) that escapes a tick is written as "email: the daily report could not be prepared: <first line>" under the same rule (`LAST_UNEXPECTED`, reset by a tick that works), warned on the terminal at the same moment, and rethrown wrapped in `Notify.Reported`; the timer's callback and `poke` pass what they catch to `_warn_escaped`, which stays silent for `Reported` and warns (scrubbed) for anything else. `_flush_audit` returns whether the audit log was written; when it was not, `LAST_TROUBLE`, `LAST_CANCEL_TROUBLE` and `LAST_UNEXPECTED` are reset, so the next tick says it again.
- **A save pokes the scheduler.** `handle_save` calls `Notify.poke()` in its own `try`, after the change log. It runs a tick `@async`, so the save's reply never waits on the network, and a day typed just before ldgr is closed is handed over within seconds. Only `handle_save` pokes; `/api/next` writes nothing. The timer (`start_schedule!`: first beat 5 s after start, then every 60 s) closes any timer left in `Main.LDGR_REPORT_TIMER` by an earlier `include("server.jl")` in the same REPL.
- **The warm-up** builds a report and its email JSON and precompiles `tick`, `Resend.send` and `Resend.cancel` by signature only; it writes nothing and touches no network. `Notify.preload` is gone. SMTPClient is no longer used (the sysimage never included it, so no rebuild).
- **The watchdog has no code on the PC:** a Resend webhook on `email.delivered` pings a healthchecks.io Cron check (`30 17 * * 1-6`, America/Guyana, grace 1–2 h), which emails the owner when a working day passes without a delivered report.
- **Never a false all-clear:** `Changes.rows_checked(from, to) -> (rows, problem)` (through `_read_log_checked`; `_rows_from` now returns `(rows, skipped, problem)`) names an unreadable log, a missing column or skipped rows; `rows_between` behaves as before. With a problem the subject starts `CHANGE LOG COULD NOT BE READ — report for …`, the "THE CHANGE LOG COULD NOT BE READ PROPERLY, … It is not a quiet day." paragraph is the **first thing in the body**, before `LDGR DAILY REPORT` (so a phone's preview shows it), the quiet sentence is left out, and step 3 sends at once instead of folding. A skipped row whose `when` is readable and outside the window is ignored; one with no readable `when` counts against every window, and so does a skipped row with any non-missing cell past the 19 columns (CSV.jl widened the table because two rows ran together on one line, and the second could be from any later day).
- **A torn line cannot hide a save** (`Changes.jl`).
  - **Writing:** `_mend_tail!` runs before each append. `_ends_in_quote(bytes)` walks the file's bytes the way CSV.jl reads them: a `"` opens a quoted cell only at the start of a cell (after a comma, a line end or the start of the file, or after nothing but spaces or tabs there, the `:lead` state), inside one `""` is a quote and a lone `"` closes it, and anywhere else a `"` is ordinary text, so `5" drawer` typed by hand is not taken for a cut (counting quotes was, and is not used). A file that ends inside a quoted cell gets `"\n`; otherwise a last line with no newline gets one. So a line cut short by a power cut or a hand edit stays on its own and cannot swallow the next save's row. A log that is empty, holds only blanks or a byte-order mark, or holds only the start of the heading line with no line break (`_no_data` against `_header_line()`; a file more than 64 bytes longer than the heading is never read for this, so a save never reads a real log to decide) counts as blank (`_blank`) and is written afresh with its header; any other damaged heading is left alone.
  - **Reading:** `_read_log_checked` reads the **bytes** and `_parse`s them with `CSV.read(bytes; types = Dict(c => String for c in COLUMNS), validate = false, delim = ',', missingstring = "", silencewarnings = true)`. Bytes, not the path: CSV.jl maps a path and on Windows releases it only on success, so a failed read left the file locked until a chance GC. A fixed delimiter: CSV.jl guesses from the first lines and one damaged line there made it pick `:`. Per-column types: with one type for all columns, a line with too many cells made CSV.jl write past the end of the columns it added (garbage, or an access violation). A parse failure is reported as "A line of the change log is damaged (for example a quotation mark that is never closed), so none of it could be read."
  - **Strict cells:** `_bool` accepts only `true`/`false` (any case); `_date`/`_dt` require the full `yyyy-mm-dd` / `yyyy-mm-dd HH:MM:SS` shape (Julia's own parsers read "2026-09-2" as 2 September); a `released` row needs its `released by`; `_text` turns invalid UTF-8 into U+FFFD (the TOML state file refuses invalid text, and one stray byte would have stopped every hand-over). A torn row is therefore skipped and named, never read as a balanced day or dated in another window.
  - The report names a skipped row as "Line N of Change Log.csv (counting the heading as line 1) could not be read and was left out." The skipped-line `@warn` has `maxlog = 1`: the log is read every minute, and the report itself names the problem.
- **Every reported edit is printed on its own** (`_later_edits`, `_edit_lines`, `_balance_lines`), because each row's `changed` holds only the step from the save before it, so printing the last alone would hide the first correction.
  - DAYS ENTERED and GAPS FILLED, after "Entered by": only same-session edits → "Changed again by X at T."; otherwise the "Its ledger had not been made yet …" line if any edit was a pending-day one, then every edit from the first reportable one (`cross_day_edit` or `pending_day`) onwards, reportable or not, each as "   Changed on <date> by <who> at <time>:" (or ", with no figure different.") with its before → after parts indented 6 spaces, then "It did not balance before: … / It balances now." when a reported edit cleared a difference and the day still balances. This covers the next-morning case: a day first saved after the send time and edited on a later date before the next report has both rows in one report.
  - CHANGES TO DAYS ALREADY SAVED prints its edits the same way, each naming who and when, and no longer ends with a single "Changed by X at T." line.
  - "It did not balance before" is taken from the **first edit printed** that carried a difference (`_was_line(io, shown, rows)`), so it matches the first before → after line and the difference the owner was last told.
  - **A ledger released by an edit** — even a same-date correction whose figures stay unlisted — is reported under CHANGES with "It was corrected on the date it was first typed in, which let a waiting ledger be made." and the release lines (`_released_lines`, shared with GAPS FILLED): the owner was told the ledger was waiting.
- **A window whose only rows are silent same-date corrections** (nothing entered, nothing reportable, no ledger waiting) says "Nothing new was entered, and every recorded day has its ledger. The only changes were corrections made on the same date a day was first typed in, which are not reported one by one." A window with no rows keeps the exact quiet sentence.
- **The session ends at the send time too (2026-09-28, the developer's decision).** A same-date correction made after that day's report had gone out used to be silent: a day saved at 4 pm with a shortage was in the 5:30 pm report, and making it balance at 6 pm the same evening was never reported. Now `Changes._session_over(first, t, send_at)` sets the `cross day edit` flag (the column keeps its name) when the edit is on a later date **or** after the send time that followed the first save, to the second (an edit stamped 17:30:00 is in the same report as a first save before it, and free). A boundary at the send time alone was rejected: a day typed at 6 pm and changed at 9 am the next morning would have become free. `after_save` takes the send time from `Changes.SEND_TIME`, which `Notify` fills with `_send_time` when it loads, so neither front door passes it; if it cannot be read, only midnight counts and the row is still written. `Changes.first_saved_at(d)` gives the first save's time (`first_seen` is its date). When the first save and the change are on the same date, CHANGES says "It was first saved on <date> at <time>." The harness in `tests/test_notify.jl` passes `send_at = nothing`, so the groups on the real clock stay time-of-day independent; group 49 tests the rule at fixed 2034 times.

## Running things safely

- **Always set `LEDGER_ROOT` to a scratch folder** before starting the server or running any test. Without it, everything is written under `v4.0/Records/`, which holds the real books.
- **Always set `LDGR_NO_DIGEST=1` and point `LDGR_NOTIFY_CONFIG` at a file that does not exist** for any test or scratch server. Without both, a daily report could be composed from scratch books and handed to Resend, to be emailed to the owner. `tests/test_notify.jl` sets them itself; nothing else does.
- **Nothing may contact Resend or the internet** from a test or a scratch run. Before anything calls into `Resend.jl`, point `Resend.API_BASE[]` at a `http://127.0.0.1:<port>` stub; `tests/test_notify.jl` does this with `HTTP.serve!` on a spare port. Leave `v4.0/notify.toml` alone and never print it (it holds, or will hold, the live Resend API key).
- **`tests/test_endtoend_edge.jl` deletes its `LEDGER_ROOT` folder when it starts** (`rm(Layout.ROOT; recursive=true, force=true)`). If `LEDGER_ROOT` is not set, that folder is `v4.0/Records/`.
- **Starting the server** (from `v4.0/`):
  1. Set `LEDGER_ROOT` to a scratch folder, `LDGR_NO_DIGEST=1`, and `LDGR_NOTIFY_CONFIG` to a file that does not exist.
  2. Set `LDGR_NO_BROWSER=1`. Without it, `start()` opens the form in a Chrome app window (`--app=`, no address bar or tabs) on the owner's screen. The owner wants that window in normal use, so don't remove the launcher from `server.jl`.
  3. Run `julia --startup-file=no server.jl 8765`.
  4. Open http://127.0.0.1:8765.
- **Picking up changes:**
  - Front-end files are read again on every request, so reloading the page picks up edits.
  - Julia edits need a server restart.
  - The server warms itself up before listening (about 9 s, or 2 s with the sysimage; `LDGR_NO_WARMUP=1` skips it), after which every endpoint answers at once. Starting with the sysimage (`julia -J sysimage/ldgr.dll ...` or `ldgr.bat`) makes both the load and the warm-up several times faster.
- **Running the tests:** the test scripts `include("Config.jl")` and similar files relative to their own folder, but they live in `tests/`. Run them from a scratch copy of `v4.0` with `tests/*.jl` copied next to the source files. `v4.0/handoff/verification.md` has a script for this.
- **This machine:** Windows 11 (Git Bash and PowerShell), with Node 24 and Google Chrome installed.
  - **Julia 1.10.12 since 2026-10-05**, through juliaup (default channel `lts`). HTTP, JSON3, DataFrames, CSV and PackageCompiler are in the default `v1.10` environment.
  - **HTTP is capped at 1.x** there (`[compat] HTTP = "1"`, currently 1.11.0). HTTP 2.x has no `HTTP.Exceptions.RequestError`, which `Resend.jl` uses, and no `HTTP.MbedTLS`, which `test_notify.jl` uses.

## Rules that must not be broken

These come from `v4.0/README.md`:

1. Never change a category `key` in `Config.jl`.
2. Never build a path outside `Layout.jl`.
3. Never calculate the closing balance for the user.
4. Never pre-fill the opening balance either.
5. Never let a Level 2 warning be dismissed with one click. The typed reason is required.
6. Never edit a Daily Journal in Excel.
7. Never change the server bind address from 127.0.0.1.
8. Don't run two servers against the same Records folder.

These come from the code comments ("Handover §4"):

- The browser never decides how severe a warning is. It shows the level, code and message that the server's checks return.
- The front end holds no category names of its own. The form is built from `/api/config`.

## UI principle

The form's appeal is how simple it is. The people using it are non-technical, non-accountant clinic staff. That means:

- plain words
- one obvious main action per screen
- no extra features

The look can be more refined, modern and minimal, but it stays in the existing green and cream colours (the tokens at the top of `v4.0/public/styles.css`).
